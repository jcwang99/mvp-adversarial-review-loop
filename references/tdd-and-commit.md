# TDD、修复与提交协议

## 实现代理任务模板

```text
你是唯一的实现代理，只处理 finding [标准 ID，如 R1-F001-SEC]。
现状与证据：[主代理裁决]
必须重现的反例：[完整前提、步骤和期望/实际]
原始 reproduction 代码路径：[.review-evidence/round-[N]/R[N]-F[XXX]-[CAT]/reproduce.*]（使用主代理分配的标准 ID）
验收断言：[可测试的行为]
允许改动：[文件/模块]
必须运行：[聚焦测试、回归、静态或安全检查]
禁止：[用户已有改动、无关重构、真实外部写入]
完成后返回失败测试输出、修复摘要、所有命令及结果、git diff --check、
提交哈希和未解决问题。不要替其他 finding 改代码。
```

## RED-GREEN-REFACTOR

1. **RED**：读取当前 `git status --short`，确认没有新的外部写入。
   - **优先使用评审代理提供的 reproduction 代码**：检查 `.review-evidence/round-[N]/R[N]-F[XXX]-[CAT]/` 目录（使用主代理分配的标准 ID）
   - 如果存在可运行的 reproduction 代码，直接运行它验证问题存在
   - **必须将通过合理性检查的 reproduction 代码迁移到项目测试套件**：
     - 确定项目测试目录位置（如 `tests/`、`__tests__/`、`src/**/*.test.js`）
     - 将 reproduction 代码改编为项目测试格式（调整导入路径、fixture 路径、断言库）
     - 保留 `.review-evidence/` 中的原始文件作为审计证据
     - 在项目测试套件中创建新测试文件或添加到相关测试文件
     - 测试文件命名应反映 finding ID，如 `security-R1-F001-SEC.test.js` 或在现有测试中添加注释 `// R1-F001-SEC`
   - 运行项目测试套件中的新测试，保存”按预期失败”的输出
   - 若 reproduction 代码不存在或无法运行，说明原因并自行构造等价测试；没有失败证据不得改实现
2. **GREEN**：实现满足验收断言的最小修复。沿用项目现有抽象和错误处理，避免顺手升级依赖、重排格式或重写不相关模块。修复后，项目测试套件中的新测试应该通过。
3. **REFACTOR**：仅在聚焦测试通过后清理重复代码或命名；每次整理后重跑聚焦测试。不要为了让测试通过而删除/放宽断言、吞掉错误、跳过权限检查或把真实调用改成无条件 mock。
4. **回归**：运行项目已存在的最小回归集，再运行完整可用的测试、类型检查、lint、构建和适用的安全扫描。记录跳过项、失败项和环境限制，不把未执行写成通过。

## 工作区与暂存隔离

共享工作区可能已有用户改动。实现代理必须在开始和提交前各执行一次 `git status --short`，比较基线；只暂存自己为当前 finding 新增或修改的明确路径，例如 `git add -- path/to/test path/to/source`，禁止 `git add -A` 或 `git commit -am`。若同一文件同时含有用户改动，先停止并让主代理决定是否能安全分块；不能安全分块就不提交。

提交前至少执行：

```text
git diff --check
git diff --cached --stat
git diff --cached
```

检查秘密、凭据、生成物、日志和大文件没有被暂存。提交信息应包含 finding ID，推荐格式：

```text
fix(review): [ID] concise behavior being corrected
```

**提交内容必须包含**：
1. 源代码修复
2. **项目测试套件中的新测试**（从 `.review-evidence/` 改编而来）
3. 必要的配置或依赖更新

**.review-evidence/ 目录不提交到本次修复 commit**：
- 证据目录应该在评审开始时就已提交（或在每轮评审后集中提交）
- 修复 commit 只包含源代码和测试的实质性变更
- 避免混淆"审计证据"和"产品代码"的边界

提交成功后返回完整哈希。若提交钩子失败，修复钩子报告的问题并重新检查差异；不要绕过钩子。若仓库没有 Git 或用户明确要求不提交，返回 `commit: unavailable`，由主代理在最终报告说明。

## 失败处理

- 聚焦测试没有按预期失败：撤销刚添加的测试改动或保留为诊断，由主代理重新确认 finding；不能继续猜测实现。
- 修复后测试仍失败：区分代码失败、测试错误和环境故障，保留原始输出；最多做有理由的修正，不以无限重试代替诊断。
- 完整回归失败：暂停后续低优先级 finding，判断是否为回归；必要时创建更高优先级 finding。
- 需要架构改动、破坏性迁移、真实凭据或生产数据：停止并请求主代理确认范围；不得擅自扩大任务。
- 修复无法安全隔离用户改动：不提交，给出最小人工操作建议和阻塞证据。

## 主代理验收清单

只有全部满足才把提交交给独立终审：

- RED 阶段失败证据与原始反例一致。
- **通过合理性检查的 reproduction 代码已迁移到项目测试套件**，测试文件已添加或更新。
- 修复最小、可读、符合现有契约，且新增测试锁定回归。
- 聚焦和回归命令的实际结果已记录；失败/跳过没有被隐藏。
- 提交只包含当前 finding（源代码 + 项目测试），`git diff --check` 通过，用户改动未被覆盖。
- commit、测试、反例和 finding ID 已写入轮次台账。
- `.review-evidence/` 目录的原始文件保持完整（作为审计证据，不在修复 commit 中）。
